# Chat-style Feed Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace MicroBin's paste form with a single chat-style feed: paste, drop or + to add text, links, images and files; live updates across devices; search; per-entry expiry.

**Architecture:** A new `src/feed/` module owns everything: an SQLite store with a change log (`store.rs`), server-side rendering of entry bodies (`render.rs`), a JSON API (`api.rs`, `upload.rs`) and a few HTML pages (`pages.rs`). The browser renders the feed frame (rows, day dividers, actions) in plain JavaScript and polls a change log every 2 s for live updates. All legacy MicroBin endpoints, encryption, privacy, burn-after and telemetry are deleted.

**Tech Stack:** Rust (edition 2021, rust-version 1.88), actix-web 4, actix-multipart, askama 0.10, rusqlite (bundled), pulldown-cmark + ammonia (new), qrcode-generator, rust-embed; plain JS/CSS in `templates/assets/`; highlight.js (already bundled); Playwright for e2e.

**Spec:** `docs/superpowers/specs/2026-11-06-chat-feed-design.md`
**Visual reference:** `docs/superpowers/specs/2026-11-06-chat-feed-mockup.html` (open in a browser, choose "B · Stream"). Its CSS tokens, layout-B rules and paste handler are the starting point for the real UI.

## Global Constraints

- Toolchain: no cargo on PATH here. Run every cargo command as
  `nix-shell -p cargo rustc gcc gnumake perl pkg-config --run '<cmd>'` (written `RUN '<cmd>'` below).
- Stack stays: actix-web, askama templates, plain JavaScript, no frontend framework, no JS build step.
- Feed code never reads the global `ARGS`; it gets a `FeedConfig` so it can be tested (`ARGS` parses the process args and breaks under `cargo test`).
- Storage: database `<data_dir>/feed.sqlite`, files `<data_dir>/feed_files/<id>/<name>`. Never read, write or delete `database.sqlite`, `database.json`, `attachments/` or `public/`.
- Entry IDs: `INTEGER PRIMARY KEY AUTOINCREMENT`, never reused. URLs use the plain integer.
- Expiry choices are exactly `never`, `1h`, `1d`, `1w` (labels "Never", "1 hour", "1 day", "1 week"). Default for new entries: `never`, changeable on `/settings`, stored in the DB.
- No burn-after, privacy levels, encryption, uploader password, editing, link previews, telemetry or update checks. No outgoing network requests at all.
- Every text entry is rendered as markdown, soft line breaks become `<br>`, output sanitized with ammonia. Copy always yields the raw text.
- Per-file upload limit: `MICROBIN_MAX_FILE_SIZE_MB`, default `2048`.
- Feed batch size: 50 entries. Search returns at most 50, newest first. Live poll interval: 2000 ms while the tab is visible.
- Optional HTTP basic auth (`MICROBIN_BASIC_AUTH_USERNAME/PASSWORD`) stays as is; off by default.
- Commits: conventional format (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`), ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. A pasted screenshot that the browser exposes only through `clipboardData.items` (not `.files`), or several screenshots all named `image.png`: each is staged once with a unique `screenshot-<ms>.png` name. Test: Task 8.
2. An upload that fails (file over the limit, server down): the text and staged files stay in the composer and an error shows; nothing is half-created on the server. Tests: Task 4 (413, no entries, temp files gone) and Task 8.
3. A phone tab that slept while entries were added and deleted elsewhere: on resume it catches up with no duplicates and no ghosts of deleted entries. Tests: Task 2 (`changes_since` add-then-delete) and Task 9.
4. Hostile or odd content: `<script>` and `javascript:` in markdown, file names with `../`, spaces or non-ASCII. Tests: Task 2 (file name) and Task 3 (sanitizing).
5. A long history and a jump into the middle: opening stays fast, scrolling up loads batches, and while viewing a search result in the middle, new live entries do not get appended out of order. Tests: Task 2 (paging with 120 entries) and Task 10.

### Task 2: SQLite store with change log

**Files:**
- Create: `src/feed/store.rs`
- Modify: `src/feed/mod.rs`

**Interfaces:**
- Consumes: Task 1 types.
- Produces:
  - `pub enum StoreError { Db(rusqlite::Error), Io(std::io::Error) }` with `From` impls and `Display`; `pub type StoreResult<T> = Result<T, StoreError>`.
  - `pub enum PageQuery { Latest, Before(i64), After(i64), Around(i64) }`
  - `pub struct Page { pub entries: Vec<Entry>, pub has_before: bool, pub has_after: bool }` (entries ascending by id)
  - `pub struct Changes { pub seq: i64, pub upserted: Vec<Entry>, pub removed: Vec<i64> }`
  - `pub struct Store` with:
    - `pub fn open(data_dir: &Path) -> StoreResult<Store>`: creates `feed_files/` and the tables `entries(id INTEGER PRIMARY KEY AUTOINCREMENT, kind TEXT, text TEXT, file_name TEXT, file_size INTEGER, created INTEGER, expires INTEGER NULL)`, `changes(seq INTEGER PRIMARY KEY AUTOINCREMENT, entry_id INTEGER)`, `settings(key TEXT PRIMARY KEY, value TEXT)`.
    - `pub fn insert_text(&mut self, text: &str, now: i64) -> StoreResult<Entry>`
    - `pub fn insert_file(&mut self, name: &str, temp: &Path, size: u64, now: i64) -> StoreResult<Entry>`: one transaction: insert row, `fs::rename` temp into `feed_files/<id>/<safe name>`, log change, commit. On rename failure, roll back.
    - `pub fn get(&self, id: i64, now: i64) -> StoreResult<Option<Entry>>`: an expired entry counts as missing.
    - `pub fn file_path(&self, entry: &Entry) -> Option<PathBuf>`
    - `pub fn page(&self, q: PageQuery, limit: usize, now: i64) -> StoreResult<Page>`: `Around(id)` returns up to `limit/2` before, the entry itself and up to `limit/2` after.
    - `pub fn delete(&mut self, id: i64) -> StoreResult<bool>`: removes the row and `feed_files/<id>/`, logs a change.
    - `pub fn set_expiry(&mut self, id: i64, expiry: Expiry, now: i64) -> StoreResult<Option<Entry>>`: logs a change.
    - `pub fn sweep_expired(&mut self, now: i64) -> StoreResult<Vec<i64>>`: deletes every entry with `expires <= now` the same way as `delete`.
    - `pub fn changes_since(&self, seq: i64, now: i64) -> StoreResult<Changes>`: distinct entry ids from `changes` with `seq > since`; ids that still exist go to `upserted` (current state, ascending), the rest to `removed`. `seq` is the max seq (or `since` when there are none).
    - `pub fn current_seq(&self) -> StoreResult<i64>`, `pub fn count(&self, now: i64) -> StoreResult<i64>`
    - `pub fn search(&self, query: &str, limit: usize, now: i64) -> StoreResult<Vec<Entry>>`: case-insensitive substring on `text` and `file_name` (`LIKE ... ESCAPE '\'`, with `%`, `_` and `\` escaped), newest first.
    - `pub fn default_expiry(&self) -> StoreResult<Expiry>` (missing → `Never`), `pub fn set_default_expiry(&mut self, e: Expiry) -> StoreResult<()>`
  - Inserts apply `default_expiry().deadline(now)`.

### Task 4: JSON API and upload

**Files:**
- Create: `src/feed/api.rs`, `src/feed/upload.rs`
- Modify: `src/feed/mod.rs`

**Interfaces:**
- Consumes: Tasks 1–3.
- Produces (in `mod.rs`):
  - `#[derive(Clone)] pub struct FeedConfig { pub data_dir: PathBuf, pub max_file_bytes: u64 }`
  - `pub struct FeedState { pub store: Mutex<Store>, pub config: FeedConfig }` and `pub fn now() -> i64` (unix seconds).
  - `pub fn configure(cfg: &mut web::ServiceConfig)` registering all feed routes (pages added in Task 5).
- Routes. Every handler first runs `sweep_expired(now)`. Errors return JSON `{"error": "<message>"}`.
  - `GET /api/entries?before=&after=&around=` (at most one; none = `Latest`; limit 50) → `{"entries": [EntryJson], "has_before", "has_after", "count", "seq"}`
  - `GET /api/changes?since=<seq>` → `{"seq", "upserted": [EntryJson], "removed": [id], "count"}`
  - `GET /api/search?q=` → `{"entries": [EntryJson]}`; empty or whitespace `q` → 400.
  - `DELETE /api/entries/{id}` → 204, or 404.
  - `PUT /api/entries/{id}/expiry` with JSON `{"expiry": "1d"}` → 200 `EntryJson`; unknown value → 400; missing entry → 404.
  - `POST /api/entries` multipart: optional field `text`, repeated field `file`. Each file streams to `<data_dir>/feed_files/tmp/<random>`. When a file passes `max_file_bytes`, stop, delete all temp files of this request, create nothing, return 413 `{"error": "<name> is larger than <N> MB"}`. With no text (after trim) and no files → 400. Otherwise create the text entry first, then one entry per file in received order; return 201 `{"entries": [EntryJson]}`.
